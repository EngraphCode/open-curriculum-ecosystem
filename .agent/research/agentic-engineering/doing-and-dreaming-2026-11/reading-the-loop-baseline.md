## 1. What it changes in the comparison's proposal

The comparison's section 6.2 proposed that a self-started seat's result be staged as a draft
pull request for the owner to accept, correct or close. The baseline weakens the gate in that
proposal and strengthens a different candidate.

- **Reading a proposed change is the weak gate.** The baseline's reading of the owner's report
  (its verdict 3) cites the one memory method with reliable gains, which admits a lesson only
  after running it on real work, because "compression can widen a rule or drop a constraint,
  and the text offers no way to tell" (E-332). Cheap validation made a system accept fewer
  updates, not better ones (E-324).
- **The Practice's own measurement says the same in other words.** Written lessons with homes
  recurred; what changed a rate was an instrument (comparison, section 2.3). And my reflection
  noted that review is where the estate's cost has gone. Three sources now agree that a
  lesson's test is execution.
- **So candidate 6.3 gains on 6.2.** The comparison's third candidate was to give skill
  evaluation a baseline that can discriminate. The baseline names that instrument as the
  field's one worked method for showing a lesson changed anything: "evaluate the same held-out
  work with the stored artefact available and with it switched off" (E-320). The Practice
  already has it for 16 of 78 skills. It has used it more than this file first said: nineteen
  runs across five skills are kept from September, beside the one of October that the
  comparison cites.

What follows for the review, and not for me to settle: whether the first experiment should be
judged by a person reading its output, or by something it has to pass.

## 2. Where the baseline and the Hermes study meet, and one tension

- **Agreement.** The baseline's verdict 6 is that an agent writing its own memory "is easy to
  build and has not been shown to work reliably". The Hermes study found a system that does
  exactly that, automatically, and records nothing that would show whether it works. The
  baseline's findings point to that study as a mechanism-level account of one such system.
- **A tension to resolve in review.** The baseline's verdict 11 is that no source it read
  describes "a standing intention to learn", held with the code and woken by a clock. The
  Hermes study describes something close: a fixed review prompt in the product's code, started
  by counters, and a curator started by a timer with an idle test. Two things separate it from
  what verdict 11 looks for. The intention is held with the product and not with the user's
  repository; and its triggers are counters inside a running session, with the timer checked
  when a session or a gateway process is already up. Whether Hermes is a counter-example to
  verdict 11 or a near miss is a judgement about what "held with the code" means. I think it
  is a near miss. I have not asked the baseline's author, and verdict 11 does not mention the
  study.

## 3. What it adds that neither earlier piece had

1. **Clocks are the rare trigger in the wild.** Of 217 loops found in 36,487 public
   repositories, 21 ran on a schedule and 180 on events (E-303). The node's first question
   lists a schedule, a computed signal and an event such as a session's end. The field's
   practice leans to events.
2. **Bounding is common where anyone looked closely.** A spending or turn limit appeared in
   101 of 256 inspected repositories (E-304), while shipped harnesses often have a stop that
   "ships disabled" or "defaults to infinity" (E-350). The field's unit of account is "cost per
   accepted change" (E-08). This bears on the node's sixth question and sits beside the
   owner's word, given for the Attendant, that cost is recorded and not put in front of a
   running agent.
3. **Agreement among agents is not evidence.** More than 80 agents endorsed a finding that was
   false, and a unanimous kill removed a true one; an empirical test was the control that held
   (E-345, E-346). This presses on two things in the estate: the review quorum for graduations,
   which is several reviewers of one model family; and this strand's own two reviews, which
   were the same.
4. **Selection by surprise can amplify an accident.** One paper found a fallback that happened
   to work once was reinforced, "Memories are 'contagious'", and that results depended on the
   order tasks arrived in (E-313, E-312). The Practice captures by surprise and promotes on the
   first instance. It also has a rule that one instance is an observation and not a pattern.
   Those two pull against each other, and this is outside evidence for the second.
5. **Self-written guidance did worse than curated guidance on one benchmark.** Human-curated
   skills gained 16.2 points; skills a model wrote for itself from the task description lost
   1.3 (E-333). The Practice's guidance is mostly agent-written and owner-corrected, which is
   neither case. The baseline is clear that every bridge from these papers to guidance files
   in a working codebase is untested.
6. **Recombining is the step the papers trust least.** A single global document "collapses into
   generic discipline" (E-239). My reflection on the owner's report did not flag this step at
   all; I read the report's four properties as a set and pressed on forgetting. The
   consolidation skill's cross-session scan asks exactly for recombination: what the sessions
   know together that none knows alone.
